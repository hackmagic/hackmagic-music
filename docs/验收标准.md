# 验收标准（Acceptance Criteria）

> **强制规则**：任何功能 / 修复 / 重构在宣布"完成"之前，必须按本文档核对，并把结论追加到 §7 验收记录。
> **未通过 §2 / §3 / §6 闸门的改动，不得提交、不得计入"已完成"。**

配套可执行脚本：`./verify.sh`（快速闸门）、`./verify.sh --full`（含 clippy + 测试）、`./verify.sh --full --size`（含 Release 体积）。

---

## 0. 这份文档要解决什么

历史问题：功能"写完了"就直接记为完成，缺少统一判定标准与证据留存，导致
① 同一个问题反复出现（如 UI 线程阻塞播放调用已犯两次）；
② 无法回答"这个功能到底验没验过"；
③ 文档之间口径不一致（曾经同时存在"542 测试通过"和"549 测试通过"两种记录）。

因此本文档把"完成"重新定义为：**代码 + 闸门全绿 + 功能实测证据 + 验收记录**，四者缺一不可。

| 等级 | 含义 | 谁执行 | 是否阻断"完成" |
|---|---|---|---|
| **G0 闸门** | 编译 / 静态规约 / 测试 | `./verify.sh --full`（自动） | ✅ 必须全绿 |
| **G1 模块功能** | 本次改动涉及模块的实际功能 | 人工操作 + 证据 | ✅ 必须实测 |
| **G2 一致性** | 与原版 MusicPlayer2 的界面/交互对齐 | AI 截图审查 + 人工 | ⚠️ 不阻断，但需记录差异 |
| **G3 交付** | Release 体积 / 启动冒烟 / 文档同步 | `./verify.sh --size` + 人工 | ✅ 必须通过 |

状态图例：

- ✅ **已验收** —— 有**运行实测**证据（命令输出 / 日志 / 截图），并注明日期与来源
- ⚠️ **部分** —— 代码已实现但仅静态验证，或仅覆盖了部分场景（须列出未覆盖项）
- ❌ **未验收** —— 无任何实测证据
- 🚫 **已知例外** —— 明确不修/不可修，附原因（见 §6）

> 注意：**"代码已实现" 不等于 "已验收"**。仅仅存在实现 + clippy 通过，状态只能记 ⚠️。

## 2. G0 通用闸门（每次改动必跑）

一条命令：`./verify.sh --full`

| 编号 | 闸门 | 命令 | 通过标准 |
|---|---|---|---|
| G0-1 | Debug 编译 | `cargo build` | 无 error |
| G0-2 | 静态检查 | `cargo clippy --all-targets` | **0 警告 0 错误** |
| G0-3 | 单元测试 | `cargo test --lib` | 0 failed，且通过数 **≥ 551**（只增不减） |
| G0-4 | 集成测试 | `cargo test`（含 `tests/ai_pipeline.rs`） | 全绿；hermetic，无需 ONNX 模型 |
| G0-5 | `catch_unwind` 缺席 | `grep -rn catch_unwind src --include=*.rs` | **必须为空**。Release 档启用 `panic="abort"`，引入 `catch_unwind` 会**静默失效**（catch 不到直接 abort） |
| G0-6 | GUI 不用 stdout | `grep -rn "println!\|eprintln!" src/gui` | **必须为空**，GUI 一律走 `tracing`（写 `hm_gui.log`） |
| G0-7 | GUI 文案不硬编码 | 见 `verify.sh` 的 UI-API 正则 | **必须为空**，所有文案走 `gui/i18n.rs` 的 `Tr`（EN/ZH 双份齐全由**编译器强制**） |
| G0-8 | `unwrap/expect` 棘轮 | `verify.sh` 内嵌 awk | 生产代码 ≤ **369**（只允许下降） |
| G0-9 | 平台门控 | 人工检查 | 改动 `smtc`/`tray`/`hotkey`/`mci_engine` 时保留 `#[cfg(target_os = "windows")]` |

**G0-8 的说明**（重要，避免误判）：实测生产代码（`#[cfg(test)]` 之外）`unwrap()/expect()` 共 **369** 处（2026-10-13 自 376 降：vecdb 改用 `PoisonError::into_inner` 消除锁 unwrap），
其中 **308** 处是 `Mutex/RwLock 的 .lock()/.read()/.write().unwrap()`（仅锁中毒时 panic，风险低），
其余 **68** 处为真实 unwrap。当前约定是**棘轮**：新代码不得增加该数字（即新代码必须遵守"生产代码无 unwrap"）。

## 3. G1 代码规约闸门（写代码时自查）

| 编号 | 规约 | 判定 |
|---|---|---|
| G1-1 | GUI 文案走 `Tr` | 新增/修改任何界面文案，必须同时补 `i18n.rs` 的 EN + ZH（漏一个直接编译不过） |
| G1-2 | 播放器调用不在 UI 线程 | `play` / `pause` / `stop` / `seek` / `play_file` 一律 `runtime().spawn_blocking`。**历史事故：BASS `pause()` 自死锁；在线音源 `play_file(远程URL)` 冻结窗口** |
| G1-3 | 错误处理 | 用 `thiserror`（`src/error.rs`）；库代码不 panic；不用 `anyhow`（项目未依赖） |
| G1-4 | 日志 | `tracing`，不用 `println!`/`eprintln!`；CLI 的输出用 `println!` 属正常（**仅限 `src/commands/`、`src/bin/` 与 `main.rs`**） |
| G1-5 | GPUI 陷阱 | 改 GUI 前先读 `.workbuddy/skills/gpui-gotchas/SKILL.md`；GUI 必须跑在 8 MB 栈线程（`src/bin/gui.rs`） |
| G1-6 | 文档同步 | 架构/构建约定变更 → 改 `AGENTS.md`；本轮事实 → 追加 `监控进度.md`；缺陷状态 → 改 `docs/缺陷分析与改进计划.md` |

## 6. 已知例外（见到这些**不算失败**）

1. **关停时 3 条 gpui ERROR**：`window not found` / `HRESULT(0x80040102)` / `HRESULT(0x80070578)`。
   根因是 gpui 0.2.2 `WindowsWindow::Drop` 对已销毁 HWND 重复调用，依赖已钉死、应用侧不可修，无资源泄漏。
   详见 `docs/ai_ui_testing.md`。
2. **截图 aHash 相似度只有 30%~50%**：与原版是两套 UI 设计，属预期；精细对比靠 AI 视觉审查而非哈希分数。
3. **`start.bat` 历史不可用**：已修为"缺二进制则先 `cargo build` 再启动"，不要再用旧的 Electron 流程。
4. **RPC 在 async 上下文里同步 dispatch**：`rpc.rs` 的 axum handler 直接调用 `commands::dispatch`，
   而多个命令内部会 `tokio::runtime::Runtime::new().block_on(...)`。
   ⚠️ **不要把这些 `Runtime::new()` 直接替换成共享的 `hm::runtime()`** —— 在共享 runtime 上 `block_on` 会 panic。
   要收敛必须先把 RPC 派发改成 `spawn_blocking`。
5. **`unwrap/expect` 存量 369 处**（2026-10-13 起）：属历史债，按棘轮处理（不得增加），不要求本轮清零。

## 一、UI 布局与原版差异对比

### 1.1 原版 MusicPlayer2 的界面构成

原版是 MFC 自绘（`CUIWindow` + 多套 XML 皮肤），主窗口由 `CMusicPlayerDlg` 组织：

- **左侧主绘图区**：专辑封面 + 歌词（卡拉 OK 样式、可翻译）+ FFT 频谱柱状图 + 曲目信息，可在多套皮肤间切换（`classical_control_bar.xml` 等，Ctrl+1…0）。
- **右侧播放列表**：`CPlayListCtrl`，可停靠 / 浮动（`CFloatPlaylistDlg`）；顶部有 Add/Delete/Sort/Playlist 工具栏；带路径框、搜索框、媒体库按钮。
- **底部播放控制条**：自绘播放/暂停、停止、上下首、进度条、音量条（跟随鼠标滚轮）。
- **自绘标题栏按钮**：最小化 / 最大化 / 迷你模式 / 全屏 / 切换界面 / 设置 / 深色，可在外观设置里逐项开关。
- **状态栏**：可"总是显示"，展示帧率 / 下一首。
- **托盘图标**：`CNotifyIcon`，右键菜单控制播放。
- **迷你模式**：独立紧凑窗口 `CMiniModeDlg`。
- **桌面歌词**：独立透明窗口 `CDesktopLyric`（可锁定 / 双行 / 背景穿透 / 预设方案）。

### 1.2 当前实现界面

活动 UI 在 `src/gui/mod.rs` 的 `MusicPlayer::render()`（mod.rs:511）：

- **顶部**：`layout::title_bar`（程序图标 + 标题 + 菜单/设置/最小化/最大化/关闭按钮）—— 非自绘皮肤，是 gpui-component 标准按钮。
- **菜单栏**：`render_menu_bar`（mod.rs:997）7 个下拉。
- **左图标栏**：`icon_sidebar`（mod.rs:154 区域附近）—— queue/folders/playlists/recent/media/search/lyrics 7 个图标按钮，点击切换 `Panel`（Playlist/MediaLib/Search/Lyrics/LyricEditor/LyricDownload/Equalizer/Settings）。
- **主内容区**：依据 `Panel` 渲染——播放列表、媒体库、搜索、歌词面板、歌词编辑器、歌词下载、均衡器、设置。
- **控制条**：底部 `control_bar` 风格（实际在 render 内联），含 prev/play/next/stop/rew/ff/repeat/mute + 进度 + 音量；还有 `render_spectrum_strip`（mod.rs:3302）频谱条。
- **迷你模式**：View 菜单 `s_mini_mode`（mod.rs:1459）仅 `window.resize(340×520)`，**无专用迷你布局**；退出时硬编码恢复 `1200×800` 而非用户原尺寸。

## 三、已知 Bug 与修复方案

严重度：🔴 P0 阻断体验　🟠 P1 重要　🟡 P2 一般

### B1 🔴 播放时 UI 冻结（进度条/频谱/歌词不更新）
- **现象**：点播放后声音正常，但进度条不动、频谱静止、歌词不滚动，直到移动鼠标/点击才偶发刷新。
- **根因**：`MusicPlayer::render()`（mod.rs:511）在开头调用 `poll_player_state`（mod.rs:304）读取 `player` 状态，但渲染只在 GPUI 认为视图"脏"时发生。代码显式写了注释"NOTE: do NOT call cx.notify() here"（mod.rs:513），且全仓**无任何 `set_interval` / 定时 `cx.notify()` / 动画循环**（`bin/gui.rs` 仅 `Application::new().run` 打开窗口）。因此没有事件驱动重绘，播放中界面冻结。
- **修复（红-绿 TDD）**：
  1. 在 `MusicPlayer::new` 之后、`Root::new` 之前，用 `cx.spawn` 或 `window.set_interval` 启动一个 ~30fps 的定时器，回调里调用 `cx.notify()` 触发重绘（或直接读 `player` 状态更新 model 并 `cx.notify`）。
  2. 把 `poll_player_state` 的逻辑从 `render()` 顶部移到定时器回调中（render 不应做副作用轮询）。
  3. 增加测试：用 mock `Player` 推进 position，断言 model 在定时器 tick 后更新。
- **验证**：`cargo run` 播放一首歌，观察进度条/频谱/歌词持续更新。

### B2 🟠 均衡器面板是装饰，滑块不接引擎
- **现象**：拖动 10 段均衡器滑块、切换预设、点"启用"，声音无任何变化；曲线预览写死 `val = 0.0`。
- **根因**：`render_equalizer_panel`（mod.rs:3146–3299）的 `on_click` 只改 `this.eq_enabled` / `this.eq_preset_name` 这两个本地字段，**从不调用 `player.eq_set(band, gain)` / `player.eq_set_preset` / `player.eq_enable`**（`core/player.rs:364/378/406` 均已实现）。曲线可视化处 `let val = 0.0_f32; // placeholder`。
- **修复**：
  1. 滑块 `on_change` 时调用 `player.eq_set(i, value as i32)`；预设按钮调用 `player.eq_set_preset(name)`；启用开关调用 `player.eq_enable(bool)`。
  2. 曲线预览读取各 `SliderState` 真实 `value()`。
  3. 把 EQ 状态（各段增益、启用、预览）持久化到 `Config`（当前 `config.rs` 无 EQ 段，需新增 `EqConfig`）。
- **验证**：播放音乐，拖动某段滑块，听感与频谱对应频段明显变化；重启后 EQ 设置保留。

### B3 🟠 专辑封面不显示（占位 div）
- **现象**：主内容区左侧是一块灰色方块，永不显示封面。

## 四、GPUI 框架下的实现可行性与限制

### 4.1 可行性结论
**原版 MusicPlayer2 的全部 UI/交互能力，在 GPUI 下均可实现**，无根本性障碍：

- **自绘布局 / 多面板 / 频谱**：GPUI 的 `div`/`h_flex`/`v_flex`/`canvas` + `Painter` 完全可画频谱柱状图、均衡器曲线、歌词高亮。当前 `render_spectrum_strip` 已证明 FFT 数据能画出来。
- **均衡器 / 音效**：纯数据驱动滑块 → 调 `Player` 引擎，技术无门槛（B2 只是没接线）。
- **歌词滚动 / 卡拉 OK**：`LyricsState` 已有时间轴 recompute，渲染层做高亮即可。
- **托盘 / SMTC / 全局热键 / 始终置顶 / 透明窗口**：属平台能力。当前 `src/tray.rs`、`src/smtc.rs`、`src/hotkey.rs` 已用 `windows` crate 实现 Windows 侧，GPUI 窗口可配合原生 HWND 操作。跨平台需分别实现 macOS(`cocoa`)/Linux(`gtk`/`dbus`)。
- **迷你模式 / 桌面歌词**：GPUI 支持开多个 `Window`；桌面歌词=独立透明 `Window` + 鼠标穿透(`SetWindowLong`)，技术上直接。
- **主题 / 深色**：颜色全由 `UiColors` 派生，切换即重绘（B4 修好后即具备）。

### 4.2 限制与坑（务必提前规避）

1. **立即模式 + 必须手动驱动重绘（最大坑，即 B1）**：GPUI 不会自动每帧重绘，播放中持续更新的内容必须靠定时器 `cx.notify()`。这是当前最致命的问题，也是 GPUI 与原版 MFC 自绘线程模型的最大差异。
2. **无原生菜单系统**：菜单依赖 `gpui-component` 的 `PopupMenu`，需手动构建每一项；**无原生加速表（accelerator table）、无系统级可访问性/屏幕阅读器支持**。原版的 `IDR_ACCELERATOR1` 全局快捷键需在 GPUI 里用 `KeyDown` 事件 + 自定义映射自行实现（当前 `hotkey.rs` 是全局钩子方案，菜单内快捷键提示也需手动维护）。
3. **文本与复杂排版**：歌词双语对齐、卡拉 OK 逐字高亮、富文本标签，GPUI 文本能力够用但都需自己布局；中文竖排/特殊字体需验证 `cosmic-text` 支持。
4. **滚动/大数据列表性能**：播放列表上万首时，`render_playlist` 一次性构建全部元素会卡；需虚拟列表（GPUI 有 `List`/`UniformList` 视图，需改造现有手写列表）。
5. **平台特定代码膨胀**：托盘/SMTC/热键/透明/置顶/打开文件位置，Windows 已实现，macOS/Linux 需另写；"跨平台一致"成本高。若目标先聚焦 Windows（与原版一致），可暂不投入跨平台。
6. **大递归渲染栈**：深嵌套元素树在 Windows 主线程易栈溢出（已用 8MB 工作线程绕过，`bin/gui.rs:60`）。复杂皮肤下仍需警惕。
7. **开发范式差异**：原版是"事件驱动 + 状态机 + 自绘线程"，GPUI 是"声明式立即模式 + 模型/视图 + 定时器"。重写 UI 时，**不要照抄 MFC 的 `OnXXX` 命令分发**，应改造成 GPUI 的 model/action/订阅模型，否则会写出大量 `std::process::exit`、`rfd` 阻塞调用和 `Arc<Player>` 全局轮询的别扭代码。

### 4.3 与原版架构的推荐对齐方式
- **播放内核**：保留 `core/player.rs` + `EngineType`（BASS/FFmpeg），这是正确抽象，原版也是三内核切换。
- **状态/事件**：引入"播放状态变更事件"（曲目切换、position tick、play/pause、ended），GUI 订阅后 `cx.notify()`，替代当前 `poll_player_state` 轮询。
- **UI 分治**：把"面板"做成独立 `View`（PlaylistView / LyricView / EqView / MediaLibView / SettingsView），主窗口做布局容器，而非现在 `MusicPlayer` 一个 3396 行巨型 `render`。这能显著降复杂度、便于 TDD。
- **菜单**：抽"命令表"（`CommandId` → handler），既驱动菜单也驱动快捷键，避免菜单和快捷键逻辑重复。
